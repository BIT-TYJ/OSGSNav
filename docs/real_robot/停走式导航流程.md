# IEVE 云服务器与 NUC 基于 ZeroMQ 的停走式实机导航流程

## 1. 目标与核心结论

本文针对 `/nas_ds925/tyj/IEVE`，设计一种云服务器运行 IEVE/MinAV/3DGS，机器人 NUC 连接相机、Mid-360、LIO 和底盘的停走式导航方案。

核心结论：

1. 相机在 NUC 上固定 30 Hz 采集，NUC 只缓存最新同步 RGB-D，不向云端持续推送 30 Hz 视频。
2. 每个停走周期只在机器人停车稳定后，由 NUC 向云端发送一组最新 RGB-D、曝光时刻位姿、内参和局部 LiDAR 栅格。
3. 云端完成 IEVE、二维语义地图、3DGS、MinAV 和 FMM 计算，只返回一个高层的“本步运动计划”，例如 odom 下的 STG 或相对旋转角。
4. NUC 使用实时 odom 在本地以 10-20 Hz 闭环执行该计划，单次运动受最大时间和最大距离限制。
5. NUC 上的 LiDAR 安全层是最终 `/cmd_vel` 的唯一发布者。云端不能直接控制电机，也不能绕过 NUC 安全层。
6. 云端计算慢、ZMQ 断线或网络超时时，NUC 保持停车；重连后不能自动重放旧动作。

云端与 NUC 的职责边界如下：

| 功能 | 云服务器 | NUC |
|---|---|---|
| 30 Hz RGB-D 驱动和最新帧缓存 | 否 | 是 |
| Mid-360、IMU、LIO/TF | 否 | 是 |
| 曝光时刻位姿插值 | 可复核 | 是，权威结果 |
| Detectron2/实例检测 | 是 | 否 |
| IEVE/MinAV/3DGS | 是 | 否 |
| 二维语义地图和 FMM | 是 | 只执行结果 |
| 每步 STG/旋转意图生成 | 是 | 校验后执行 |
| 10-20 Hz 底盘闭环 | 否 | 是 |
| LiDAR 近障、超时、急停 | 否 | 是 |
| 最终 `/cmd_vel` | 绝对禁止 | 是，且只有安全层发布 |

## 2. 为什么不能让云端发送连续速度

不要采用下面的结构：

```text
云端 IEVE -> ZMQ 20 Hz Twist -> NUC -> 电机
```

原因包括：

- 网络时延和抖动会直接进入控制回路。
- 云端 GPU 计算可能阻塞数秒，速度刷新会中断。
- TCP 重连后可能收到积压的旧命令。
- 云端使用的是上传图像对应的历史位姿，而 NUC 掌握当前实时位姿和障碍物。
- 云端进程崩溃时不能保证及时发送零速度。

正确结构是：

```text
云端每周期只发送一次：STG + 本步约束
                       |
                       v
NUC 用实时 odom 以 20 Hz 计算 v/omega
                       |
                       v
NUC LiDAR Safety Supervisor
                       |
                       v
                    /cmd_vel
```

云端回答“这一步往哪里走”，NUC 决定“此刻怎样安全地走”。

## 3. 总体部署架构

### 3.1 云服务器进程

建议云端运行三个逻辑模块，可以在一个服务进程中由不同线程/进程承载：

```text
ZmqCloudIo
  - ROUTER sockets
  - 心跳、ACK、去重、会话管理
  - 不能被 GPU 推理阻塞

RemoteRobotBackend
  - 将 NUC Snapshot 转为 IEVE obs/info
  - 将 FMMResult 转为 MotionPlan
  - 等待本步执行结果和下一帧

IEVE Worker
  - Detectron2
  - semantic map
  - 3DGS
  - MinAV
  - FMM
```

ZMQ socket 只能由创建它的 I/O 线程使用，不能从 IEVE GPU Worker 线程直接调用同一个 socket。I/O 线程和 Worker 之间使用本机 `queue.Queue` 或 multiprocessing queue 传递 Python 数据结构。

### 3.2 NUC 进程

建议 NUC 使用 ROS 2 管理硬件，并将跨机器通信限定在一个 ZMQ Bridge 中：

```text
Orbbec/Femto Bolt driver -> LatestRgbdBuffer ----+
                                                |
Mid-360 + FAST-LIO2/Point-LIO -> PoseBuffer -----+-> StopGoCoordinator
                                                |          |
local LiDAR costmap ----------------------------+          |
                                                           v
                                                    ZmqRobotClient
                                                           |
                                                      云服务器

MotionPlan <- ZmqRobotClient
     |
StopGoCoordinator
     |
StgController (20 Hz) -> /ieve/cmd_vel_raw
     |
SafetySupervisor <- Mid-360/odom/e-stop
     |
  /cmd_vel
```

推荐把以下组件分成独立进程：

1. `ieve_nuc_bridge`：相机缓存、位姿插值、ZMQ、停走状态机。
2. `ieve_stg_controller`：20 Hz 本地闭环控制。
3. `ieve_safety_supervisor`：独立安全进程，唯一发布 `/cmd_vel`。

即使 `ieve_nuc_bridge` 因图像编码或 ZMQ 异常退出，Safety Supervisor 也会因 `/ieve/cmd_vel_raw` 或 motion authorization 超时而停车。

## 4. 网络与 ZMQ 通道分配

### 4.1 推荐的三个通道

云服务器绑定端口，NUC 主动连接云服务器。这样便于 NUC 位于 NAT 或机器人局域网内时建立连接。

| 端口 | Socket 模式 | 方向 | 内容 | 可靠性要求 |
|---|---|---|---|---|
| `5555` | Cloud `ROUTER`, NUC `DEALER` | 双向 | 会话、心跳、START、PLAN、ACK、执行结果、FAULT | 必须可靠、可重试、去重 |
| `5556` | Cloud `ROUTER`, NUC `DEALER` | 双向 | 每周期一组 Snapshot multipart 和 Snapshot ACK | 一次只允许一个 in-flight snapshot |
| `5557` | Cloud `SUB`, NUC `PUB` | NUC -> Cloud | 可选的低频诊断 telemetry | 允许丢失，不参与安全决策 |

配置示例：

```text
control_endpoint  = tcp://<cloud-private-ip>:5555
snapshot_endpoint = tcp://<cloud-private-ip>:5556
telemetry_endpoint= tcp://<cloud-private-ip>:5557
```

不建议使用 REQ/REP 作为主控制通道。REQ/REP 强制严格一问一答，任意一次超时或重连都会使状态机难以恢复；ROUTER/DEALER 更适合心跳、异步推理和 ACK 重发。

### 4.2 Socket 选项

云端和 NUC 都应显式设置：

```python
socket.setsockopt(zmq.LINGER, 0)
socket.setsockopt(zmq.IMMEDIATE, 1)
socket.setsockopt(zmq.SNDHWM, 100)       # control
socket.setsockopt(zmq.RCVHWM, 100)
socket.setsockopt(zmq.SNDTIMEO, 200)
socket.setsockopt(zmq.RCVTIMEO, 200)
```

Snapshot channel 建议：

```python
socket.setsockopt(zmq.SNDHWM, 2)
socket.setsockopt(zmq.RCVHWM, 2)
socket.setsockopt(zmq.MAXMSGSIZE, 32 * 1024 * 1024)
```

NUC DEALER identity 固定为本次启动身份：

```text
robot_id = robot_01
boot_id  = 每次进程启动生成的 UUID
identity = robot_01:<boot_id>
```

不要对 multipart Snapshot 使用 `ZMQ_CONFLATE`。不同 multipart 的帧可能无法按应用预期整体替换。通过“一次只发送一个 Snapshot，收到 ACK 后才能发送下一个”的应用层规则控制积压。

### 4.3 网络安全

云服务器端口不能直接无认证暴露到公网。推荐优先级：

1. 云服务器和 NUC 先建立 WireGuard 私网，ZMQ 只监听 WireGuard 地址。
2. 防火墙只允许 NUC 的 WireGuard IP 访问 5555-5557。
3. 若无法使用 VPN，再配置 CurveZMQ 服务端/客户端密钥。
4. 密钥、私钥和 WireGuard 配置不得提交到 IEVE 仓库。

ZMQ/TCP 的可靠传输不等于动作 exactly-once。应用层仍必须使用 `boot_id`、`episode_id`、`cycle_id`、`message_id` 和 ACK 去重。

## 5. 统一消息头

所有 control 和 snapshot 消息都包含同一个 JSON header：

```json
{
  "protocol": "IEVE-ZMQ",
  "version": 1,
  "type": "SNAPSHOT",
  "robot_id": "robot_01",
  "boot_id": "8ed9...",
  "session_id": "9e72...",
  "episode_id": "real_20260727_001",
  "cycle_id": 12,
  "sequence": 84,
  "message_id": "1df0...",
  "reply_to": null,
  "sent_unix_ns": 1785140000000000000
}
```

字段语义：

| 字段 | 规则 |
|---|---|
| `protocol/version` | 不匹配立即拒绝，不做猜测性兼容 |
| `robot_id` | 机器人稳定名称 |
| `boot_id` | NUC Bridge 每次启动变化；用于废弃重启前消息 |
| `session_id` | 一次云端与 NUC 建立的逻辑会话 |
| `episode_id` | 一次目标导航任务 |
| `cycle_id` | 一次“停车采集 -> 云端计算 -> 短距离运动”的编号，单调递增 |
| `sequence` | 每个发送端单调递增的消息序号，用于诊断 |
| `message_id` | UUID，用于幂等去重 |
| `reply_to` | ACK 或 response 对应的原始 `message_id` |
| `sent_unix_ns` | 仅用于日志和网络时延估计，不用于 NUC 控制超时 |

控制超时必须使用各主机自己的 monotonic clock。不能用云端和 NUC 的 wall clock 直接计算电机安全超时。两台机器仍应运行 chrony/PTP，方便关联日志和核对相机/LiDAR 时间。

## 6. Multipart 编码规则

### 6.1 Control channel

NUC DEALER 发送：

```text
[b"IEVE1", header_json_utf8, payload_json_utf8]
```

Cloud ROUTER 接收：

```text
[dealer_identity, b"IEVE1", header_json_utf8, payload_json_utf8]
```

ROUTER/DEALER 不需要 REQ/REP 风格的空 delimiter frame。所有 JSON 必须限制最大长度并做 schema 校验。

### 6.2 Snapshot channel

Snapshot 使用 multipart，禁止 Python pickle：

```text
NUC DEALER sends:
[
  b"IEVE1",
  header_json,
  snapshot_metadata_json,
  rgb_bytes,
  depth_bytes,
  local_costmap_bytes
]
```

推荐编码：

- RGB：首轮使用 PNG 无损；带宽受限时使用 JPEG quality 90-95，并重新验证检测和特征匹配结果。
- Depth：Femto Bolt 原始 `16UC1` 可用 16-bit PNG，metadata 明确 `depth_scale_to_meter`；若内部已经转为 float32，则使用 Zstandard 压缩并明确 dtype/shape。
- local costmap：`int8` 原始数组经 Zstandard 压缩；语义保持 ROS OccupancyGrid：`-1=unknown, 0=free, 100=occupied`。

metadata 中保存每段 payload 的 encoding、shape、未压缩长度和 CRC32。TCP 已有校验，但 CRC 可以快速发现 codec 或 frame 顺序错误。

### 7.2 LiDAR costmap 与视觉 explored 必须分开

上传的 `local_costmap` 用于增强 FMM 障碍约束和可达性判断，但不能直接写入 IEVE 的视觉 `exp_pred`：

- LiDAR 360 度看到的自由空间不代表相机已经观察过该区域。
- `local_costmap` 只更新 nav obstacle/free layer。
- RGB-D 视锥和语义映射继续更新 visual explored/semantic layer。

如果首版尚未完成 LiDAR 栅格到 IEVE map 的变换，可以暂时只让 NUC Safety Supervisor 使用 LiDAR，云端 FMM 继续使用 RGB-D 障碍图；但此模式只能低速测试，随后应完成 costmap 融合。

## 8. 云端返回给 NUC 的 MotionPlan

云端不能返回 Habitat 归一化 action。统一返回物理语义的 MotionPlan：

```json
{
  "plan_id": "plan-real_20260727_001-12-01",
  "based_on_frame_id": "robot_01:real_20260727_001:12:39218",
  "kind": "STG_ODOM",
  "stg": {
    "frame": "odom",
    "x_m": 1.82,
    "y_m": -0.34,
    "yaw_rad": 0.21,
    "arrival_radius_m": 0.10
  },
  "constraints": {
    "max_motion_duration_sec": 0.50,
    "max_motion_distance_m": 0.15,
    "max_linear_mps": 0.20,
    "max_angular_rps": 0.40,
    "ttl_after_receive_ms": 1000
  },
  "planner": {
    "fmm_stop": false,
    "replan": false,
    "goal_source": "IEVE_FRONTIER",
    "target_mode": "exploration",
    "map_step": 12
  }
}
```

`kind` 只允许：

| kind | NUC 行为 |
|---|---|
| `STG_ODOM` | 使用当前 odom 闭环跟踪物理 STG |
| `ROTATE_REL` | 原地旋转指定相对角；每次建议不超过 30 度，然后重新停车采集 |
| `HOLD` | 保持停车，稍后同 cycle 或新 cycle 重新请求 |
| `TERMINAL_STOP` | 任务成功或上层决定结束，保持停车并结束 episode |
| `ABORT` | 任务异常结束，进入安全停车状态 |

`ROTATE_REL` payload 示例：

```json
{
  "kind": "ROTATE_REL",
  "relative_yaw_rad": 0.5235988,
  "constraints": {
    "max_motion_duration_sec": 1.5,
    "max_angular_rps": 0.4,
    "yaw_tolerance_rad": 0.035
  }
}
```

NUC 对云端约束只能收紧，不能放宽：

```text
effective_max_linear  = min(plan.max_linear,  nuc_hard_max_linear)
effective_max_angular = min(plan.max_angular, nuc_hard_max_angular)
effective_max_time    = min(plan.max_time,    nuc_hard_max_time)
effective_max_distance= min(plan.max_distance,nuc_hard_max_distance)
```

## 9. 每一步导航的完整消息时序

### 9.1 建立连接

```text
NUC -> Cloud: HELLO
Cloud -> NUC: HELLO_ACK(session_id, protocol_version)
NUC -> Cloud: ROBOT_STATUS(state=IDLE_STOPPED, sensors=...)
```

`HELLO` 包含机器人能力：RGB-D 分辨率、相机 encoding、是否提供 costmap、硬速度上限、ROS frame 名和软件 git commit。云端发现协议或坐标系不匹配时拒绝会话。

### 9.2 开始任务

目标图保存在云服务器，操作员在云端启动：

```text
Cloud -> NUC: START_EPISODE(episode_id, target摘要, stop_go约束)
NUC:
  motion_allowed=false
  Safety输出零速度
  检查 camera/LIO/LiDAR/base controller
NUC -> Cloud: START_ACK(accepted=true, state=STOPPING)
```

NUC 不需要接收目标图原始数据，除非 NUC 本地 UI 需要显示。IEVE 使用的 target RGB 留在云端，减少接口复杂度。

### 9.3 周期 `cycle_id=N`

| 序号 | 发送方 | 消息/本地动作 | 关键内容 |
|---|---|---|---|
| 1 | NUC 本地 | `STOPPING` | `motion_allowed=false`，最终 `/cmd_vel=0` |
| 2 | NUC 本地 | 停车确认 | 线速度、角速度连续 200 ms 低于阈值 |
| 3 | NUC 本地 | `SETTLING` | 再等待 150 ms，避免振动和运动模糊 |
| 4 | NUC 本地 | `CAPTURE` | 取第一帧时间晚于 settle 完成时刻的新 RGB-D |
| 5 | NUC 本地 | 组装 Snapshot | 插值曝光时刻 pose，冻结 costmap 和 safety 状态 |
| 6 | NUC -> Cloud | `SNAPSHOT` | multipart RGB、Depth、pose、K、costmap |
| 7 | Cloud -> NUC | `SNAPSHOT_ACK` | 已校验/已去重/进入处理队列 |
| 8 | Cloud 本地 | `PROCESSING` | IEVE、semantic map、3DGS、MinAV、FMM |
| 9 | Cloud -> NUC | `PROCESSING_STATUS` | 每 1 秒报告存活和阶段；NUC 始终停车 |
| 10 | Cloud -> NUC | `MOTION_PLAN` | `plan_id`、`based_on_frame_id`、STG、运动上限 |
| 11 | NUC 本地 | 校验计划 | episode/cycle/frame/pose drift/安全/TTL/去重 |
| 12 | NUC -> Cloud | `PLAN_ACK` | accepted 或明确 reject reason |
| 13 | NUC 本地 | `EXECUTING` | 本地 Controller 20 Hz，Safety 最终过滤 |
| 14 | NUC -> Cloud | `EXECUTION_STATUS` | 可选 2 Hz 进度，非控制必需 |
| 15 | NUC 本地 | 到达或受限停止 | 到 STG、0.5 s、0.15 m、障碍或超时 |
| 16 | NUC -> Cloud | `EXECUTION_RESULT` | 起终 pose、实际距离、耗时、结束原因、安全事件 |
| 17 | NUC 本地 | `cycle_id=N+1` | 回到 STOPPING，重新稳定采集 |

### 9.4 云端等待期间 NUC 的行为

从发送 Snapshot 到接收并接受 MotionPlan 期间：

```text
motion_allowed = false
/ieve/cmd_vel_raw = 0
/cmd_vel = 0
相机继续 30 Hz，LatestRgbdBuffer 持续覆盖
LIO/LiDAR/Safety 持续高频运行
```

云端计算 2 秒、20 秒或 100 秒都不会造成机器人继续运动，也不会积压相机帧。

### 9.5 计划到达时的 NUC 校验

NUC 只有同时满足以下条件才接受 MotionPlan：

```text
boot_id/session_id/episode_id 匹配
plan.cycle_id == current_cycle_id
based_on_frame_id == 本周期 Snapshot frame_id
状态 == WAIT_PLAN
plan_id 从未执行
收到计划后尚未超过本地 TTL
当前 safety == OK
当前 pose 与采集 pose 的平移漂移 < 0.03 m
当前 pose 与采集 pose 的 yaw 漂移 < 2 deg
STG 坐标有限且位于允许工作区
计划约束不超过 NUC 本地硬限制
```

任一条件失败，NUC 返回 `PLAN_ACK(accepted=false, reason=...)`，保持停车并开始一个新 Snapshot cycle。不能“尽量执行”不一致的旧计划。

## 10. ACK、重试与 exactly-once 动作

### 10.1 Snapshot 幂等

- NUC 一次只允许一个 Snapshot in flight。
- `SNAPSHOT_ACK` 超时后可以重发相同 `message_id/frame_id`。
- 云端以 `(robot_id, boot_id, episode_id, cycle_id, frame_id)` 去重。
- 云端收到重复 Snapshot 时返回同一 ACK，不重复更新 2D map 或 3DGS。

### 10.2 MotionPlan 幂等

- Cloud 在未收到 `PLAN_ACK` 时可以重发同一个 `plan_id`。
- NUC 保存本 episode 最近已接受和已完成的 `plan_id -> status`。
- 重复收到已接受计划时，只重发 ACK 或已有 ExecutionResult，绝不能再次执行。
- Cloud 如果要产生不同计划，必须使用新的 `plan_id`；通常还应开始新 `cycle_id` 并使用新 Snapshot。

### 10.3 重连规则

NUC 或 Cloud 任一端重启、TCP 断开或 `boot_id` 变化时：

1. NUC 立即撤销 `motion_allowed`。
2. Safety Supervisor 因授权/heartbeat 超时输出零速度。
3. 重连后状态只能是 `IDLE_STOPPED` 或 `RECOVERY_STOPPED`。
4. 旧 session、旧 plan 和旧 in-flight Snapshot 全部作废。
5. 必须重新 `HELLO -> START_EPISODE`，不能自动续跑旧动作。

## 11. 心跳与超时

### 11.1 应用心跳

Control channel 每 200 ms 双向发送一次：

```text
PING(message_id, local_monotonic_ns)
PONG(reply_to, state, current_cycle_id)
```

I/O 线程负责心跳，不能依赖正在进行 GPU 推理的 Worker。可同时启用 ZMQ transport heartbeat，但应用层状态心跳仍需保留。

### 11.2 NUC 超时表

| 条件 | 建议阈值 | NUC 动作 |
|---|---:|---|
| Control heartbeat 丢失且正在 EXECUTING | 800 ms | 立即撤销运动并停车；本步自身仍受 0.5 s 硬上限约束 |
| 等待云端 MotionPlan | 120 s | 全程停车；超时后报告 FAULT/允许人工重试 |
| Snapshot ACK | 2 s | 最多重发相同 Snapshot 3 次 |
| 相机无新同步帧 | 200 ms | 不上传、不运动 |
| LIO/odom 超时 | 200 ms | Safety 输出零速度 |
| LiDAR 超时 | 200 ms | Safety 输出零速度 |
| `/ieve/cmd_vel_raw` 超时 | 200 ms | Safety 输出零速度 |
| MotionPlan 本地 TTL | 1000 ms | 拒绝计划，重新采集 |

MotionPlan 等待超时可以很长，因为 WAIT_PLAN 期间机器人已经停车；与电机相关的 heartbeat、odom、LiDAR 和 raw command 超时必须很短且完全由 NUC 本地 monotonic clock 判断。

## 12. NUC 本地停走状态机

### 12.1 状态

```text
BOOT
  -> IDLE_STOPPED
  -> STOPPING
  -> SETTLING
  -> CAPTURE
  -> UPLOADING
  -> WAIT_PLAN
  -> VALIDATE_PLAN
  -> EXECUTING
  -> STOPPING

任意状态 -> FAULT_STOPPED
```

状态转移必须由事件驱动，不能依靠固定 `sleep()` 猜测网络或推理是否完成。只有 `SETTLING` 的物理稳定等待使用 timer。

### 12.2 本地接口

StopGoCoordinator 订阅 ROS：

| Topic | 类型 | 用途 |
|---|---|---|
| `/camera/color/image_rect` | `sensor_msgs/Image` | 30 Hz RGB |
| `/camera/aligned_depth_to_color/image_raw` | `sensor_msgs/Image` | 对齐深度 |
| `/camera/color/camera_info` | `sensor_msgs/CameraInfo` | 真实内参 |
| `/lio/odom` | `nav_msgs/Odometry` | 当前/历史 `T_odom_base` |
| `/local_costmap` | `nav_msgs/OccupancyGrid` | 上传给云端的规划障碍层 |
| `/ieve/stg_execution_status` | 自定义或标准诊断消息 | 本步执行结果 |
| `/ieve/safety_status` | 自定义或 `diagnostic_msgs` | 当前安全状态 |

StopGoCoordinator 发布 ROS：

| Topic | 类型 | 用途 |
|---|---|---|
| `/ieve/motion_allowed` | `std_msgs/Bool` | 只有 EXECUTING 为 true |
| `/ieve/stg` | `geometry_msgs/PoseStamped` | odom 下 STG |
| `/ieve/rotate_relative` | 自定义消息 | 相对旋转计划，可选 |
| `/ieve/run_state` | 自定义/诊断消息 | 状态、episode、cycle、fault |

### 12.3 停车和选帧

NUC 进入 STOPPING 后：

```text
motion_allowed=false
等待 abs(v)<0.01 m/s 且 abs(omega)<0.02 rad/s 连续 200 ms
再等待 settle_time=150 ms
记录 settle_complete_stamp
从 LatestRgbdBuffer 获取：
  frame.seq > last_uploaded_seq
  frame.capture_stamp >= settle_complete_stamp
  now - frame.capture_stamp < 100 ms
```

不能在运动一结束就上传缓存中已有的帧，因为该帧可能是在运动期间拍摄。

## 13. NUC 本地 Controller 和 Safety

### 13.1 STG Controller

Controller 只接收 odom 下 STG，使用实时 `T_odom_base(now)`：

```text
dx = stg_x - base_x
dy = stg_y - base_y
distance = hypot(dx, dy)
target_yaw = atan2(dy, dx)
yaw_error = normalize(target_yaw - base_yaw)

if not motion_allowed:
    v = 0; omega = 0
elif abs(yaw_error) > 20 deg:
    v = 0
    omega = clip(k_w * yaw_error, -w_max, w_max)
else:
    v = clip(k_v * distance, 0, v_max) * max(0, cos(yaw_error))
    omega = clip(k_w * yaw_error, -w_max, w_max)
```

以 20 Hz 发布 `/ieve/cmd_vel_raw`。任一条件结束本步：

- 到达 STG 半径 0.10 m。
- 本步运动达到 0.50 s。
- 本步累计平移达到 0.15 m。
- 相对旋转达到目标角。
- Safety stop、LIO timeout、network heartbeat timeout 或 Coordinator cancel。

### 13.2 Safety Supervisor

Safety Supervisor 订阅：

```text
/ieve/cmd_vel_raw
/ieve/motion_allowed
/lio/odom
/livox/lidar 或去畸变点云
/local_costmap
/emergency_stop
```

并且是唯一发布：

```text
/cmd_vel
```

处理优先级：

```text
人工急停/锁存故障 -> zero
LiDAR/odom/raw_cmd/motion heartbeat 超时 -> zero
motion_allowed=false -> zero
障碍进入 hard-stop swept footprint -> zero
障碍进入 slowdown footprint -> 降低线速度
否则 -> 限幅后转发 raw cmd
```

NUC 的硬速度、距离和时间上限写在本地只读配置中。云端任何消息都不能修改或放宽这些安全上限。

- 深度入口：使用 metadata 中显式单位，不能通过最大深度猜测 normalized/meter。
- Habitat SPL/success 等指标在实机模式改为独立运行指标。

### 14.8 FMM 栅格 STG 转换为 `odom`

Cloud 返回给 NUC 的 STG 必须已经是 `odom` 下的物理坐标，NUC 不应理解 IEVE 的 local map window。当前 IEVE 使用 row 表示平面 y、column 表示平面 x。设：

```text
global_row = local_stg_row + gx1
global_col = local_stg_col + gy1
resolution_m = map_resolution_cm / 100

x_internal_map = (global_col + 0.5) * resolution_m
y_internal_map = (global_row + 0.5) * resolution_m
```

RemoteRobotEnv 在 episode 第一帧保存：

```text
episode_origin_odom = [first_base_x, first_base_y, first_base_yaw]
map_center_m = map_size_cm / 100 / 2
```

在没有 `map -> odom` 额外旋转的首版中：

```text
x_stg_odom = episode_origin_x + x_internal_map - map_center_m
y_stg_odom = episode_origin_y + y_internal_map - map_center_m
```

如果 episode 内部地图轴相对 `odom` 存在初始 yaw 旋转，则必须使用完整二维刚体变换，不能只加平移。该转换必须用以下场景做单元测试：起点对应地图中心、正前方一格产生正确 odom 方向、左转 90 度后 STG 方向正确、local window 移动后同一个 global cell 仍得到相同 odom 坐标。

MotionPlan 同时携带 `based_on_frame_id` 和转换时使用的 `map_step`，便于定位坐标错误。

### 14.9 云端 I/O 不得被推理阻塞

建议线程关系：

```text
CloudIoThread:
  zmq.Poller
  heartbeat
  receive Snapshot
  send ACK/Plan
  queue.put(snapshot)

IeveWorkerThread/Process:
  snapshot = queue.get()
  process IEVE
  outgoing_plan_queue.put(plan)
```

CloudIoThread 每秒向 NUC 发送 `PROCESSING_STATUS`。即使 IEVE Worker 正在长时间 GPU 调用，心跳仍然工作。

## 16. 初始 360 度观察如何传递

当前仿真按多个转动 step 获得多视角观测。实机 ZMQ 模式也应拆分：

```text
cycle 0: 停车 -> Snapshot -> Cloud PLAN ROTATE_REL(+30 deg)
NUC: 本地转 30 deg -> 停车 -> ExecutionResult

cycle 1: 稳定 -> 新 Snapshot -> Cloud PLAN ROTATE_REL(+30 deg)
...

cycle 11: 完成 360 deg -> 新 Snapshot -> Cloud 进入正常 FMM
```

不能让 NUC 连续旋转 360 度后只上传一帧，否则 IEVE/3DGS 丢失中间 11 个视角；也不能在连续旋转时上传给慢速云端并要求逐帧响应。

## 17. 目标到达与任务结束

需要区分：

- `FMM 当前 STG 到达`：只表示本步或当前局部目标结束，应开始下一停走周期。
- `MinAV/IEVE 最终目标确认并满足成功条件`：Cloud 返回 `TERMINAL_STOP`。
- `安全障碍停止`：不是任务成功，Cloud 应根据新 Snapshot 重新规划。
- `operator abort`：Cloud 或 NUC 操作员触发 `ABORT`，NUC 锁定停车。

`TERMINAL_STOP` 时序：

```text
Cloud -> NUC: MOTION_PLAN(kind=TERMINAL_STOP)
NUC: motion_allowed=false, /cmd_vel=0, 确认底盘停止
NUC -> Cloud: PLAN_ACK + EPISODE_RESULT(stopped=true)
Cloud: 保存 3DGS/日志/任务结果，关闭 episode
```

## 19. 推荐开发顺序

### 阶段 A：协议和假机器人

1. 实现共享 `protocol.py`、JSON schema 和 multipart codec。
2. 写 NUC simulator，从磁盘循环读取一组 RGB-D/pose，不连接电机。
3. Cloud 收 Snapshot 并返回固定 `HOLD`。
4. 测试 ACK、重复 Snapshot、重复 Plan、断线和重启。

验收：任何重发都不会导致同一 plan 执行两次；重连后旧 cycle 被拒绝。

### 阶段 B：真实传感器但不接底盘

1. NUC 接相机、CameraInfo、LIO 和 costmap。
2. 构建曝光时刻 Snapshot 并上传。
3. Cloud 解码并离线运行 IEVE/3DGS。
4. 对比 NUC 原图与云端解码图，验证 depth 单位、K 和位姿。

验收：RGB/depth CRC 正确；云端 3DGS 无明显双墙；Snapshot 不积压。

### 阶段 C：Controller/Safety 独立测试

1. 不启动 Cloud，NUC 本地注入短 STG。
2. 抬轮或低速测试 Controller。
3. 逐项断开 LiDAR、odom、raw cmd 和 ZMQ heartbeat。
4. 确认 Safety 在阈值内输出零速度。

验收：`/cmd_vel` 只有 Safety publisher；所有超时和急停可靠停车。

### 阶段 D：完整停走

1. 初始速度上限 `0.05 m/s`，每步不超过 5 cm。
2. Cloud 返回真实 FMM STG。
3. 连续完成 50 个 cycle，检查 cycle/frame/plan 一一对应。
4. 人工制造 500 ms、2 s 网络延迟和临时断线。
5. 稳定后逐步提高到 `0.1 m/s`，首版不超过 `0.2 m/s`。

## 20. 必须测试的故障场景

| 测试 | 预期结果 |
|---|---|
| Cloud GPU 推理阻塞 60 秒 | NUC 全程保持停车，相机缓存不积压 |
| Cloud 进程被 kill | NUC heartbeat 超时并停车，不能继续旧 plan |
| NUC ZMQ Bridge 被 kill | Safety 因 motion authorization/raw cmd 超时停车 |
| 网络断开后恢复 | 回到 IDLE_STOPPED，重新 HELLO/START，不续跑旧动作 |
| 同一 MotionPlan 发送两次 | NUC 只执行一次，第二次返回已有状态 |
| 上一 cycle 的 Plan 延迟到达 | NUC 以 cycle/frame 不匹配拒绝 |
| Snapshot ACK 丢失 | NUC 重发相同 Snapshot，Cloud 不重复更新地图 |
| 相机掉线 | 不产生 Snapshot，不允许运动 |
| LIO 掉线 | Safety 停车，计划拒绝 |
| LiDAR 掉线 | Safety 停车，即使 Cloud 仍返回 STG |
| 深度单位配置错误 | Snapshot schema/range check 拒绝，禁止进入 3DGS |
| 当前 pose 相对采集 pose 漂移过大 | 拒绝 Plan并重新停车采集 |

网络故障可在测试机上使用 `tc netem` 注入延迟、抖动和断连；只有在底盘抬轮或安全场地内完成通信故障测试后才能落地运行。

## 22. 最小可运行闭环总结

第一版只需要实现下面的闭环，不需要传 30 Hz 视频，也不需要云端发送连续速度：

```text
NUC 停车并确认稳定
  -> 取最新 RGB-D
  -> 插值曝光时刻 pose
  -> 上传一个 Snapshot
  -> 云端 ACK 并运行 IEVE/FMM
  -> 云端返回一个带 cycle/frame/plan ID 的 STG
  -> NUC 校验并 ACK
  -> NUC 本地 20 Hz 执行最多 0.5 s 或 0.15 m
  -> LiDAR Safety 每周期过滤并最终发布 /cmd_vel
  -> NUC 停车并发送 ExecutionResult
  -> 开始下一 cycle
```

这套分工保证：云端保留 IEVE 所需的大算力；NUC 保留所有实时性和安全性；每一步导航都有明确的 Snapshot、Plan、ACK 和 ExecutionResult；任何旧消息、断线或计算阻塞都不会让机器人继续执行失效动作。
