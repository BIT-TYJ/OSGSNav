## 0. 现状与本轮目标

已知现状（以用户说明为准）：OSGSNav已经在实机上完成单目标demo；实机机载代码未在本次检查范围内，因此不假定它与服务器源码完全一致，也不要求用仿真入口覆盖已跑通的demo。

本轮目标：

1. 单目标定量对照：**OSGSNav vs. UniGoal**。
2. 连续多目标定量对照：**OSGSNav vs. UniGoal-M**。论文可沿用多目标名称OSGSNav与UniGoal-M，但表注应明确两者都是连续请求模式。
3. 主张同时覆盖正确实例到达、物理运动效率、完整任务时间及计算开销；内部匹配/定位完成不能代替实机导航成功。

必须按下面顺序推进：

```text
实机demo归档 + 两方法代码准备
           ↓
共同输入/执行接口 + 共同评测协议
           ↓
UniGoal单目标实机接入与回归
           ↓
两方法单目标pilot → 冻结版本 → 单目标正式对照
           ↓
两目标切换测试 → 五目标pilot
           ↓
冻结多目标版本 → 五目标正式对照
           ↓
配对统计、失败分析、论文表格与证据归档
```

可以并行准备多目标任务清单和日志工具，但不要跳过UniGoal单目标实机验收而直接跑五目标正式实验。

## 2. 第一步：冻结共同实验协议（先于正式采数）

负责人：实验负责人 + 评测同学；两方法调试同学共同签收。

### 2.1 共同输入与硬件条件

- [ ] 同一机器人、RGB-D相机、外部定位系统、标定、地图分辨率策略（如方法原生要求不同则明确记录）、最大线速度/角速度与统一底盘执行层。
- [ ] 两方法读取相同类型且同单位的RGB、对齐深度、相机内参、曝光时刻相机/底盘位姿。明确`T_world_camera`或其逆、坐标轴、深度单位和无效值。
- [ ] 目标输入统一为**目标RGB图像**。不向任一方法额外提供目标深度、GT目标实例mask或GT目标位置。
- [ ] 类别协议二选一并固定：两者都得到相同任务类别，或两者按事先规定自行识别类别。不要一方给类别、另一方承担识别。已有仿真`goal_cat_source=oracle`不能原样解释成实机自动识别。
- [ ] 同一帧选择/时间同步策略；优先复用已验证的最新帧缓存与停走执行机制。允许方法处理速度不同，但要记录丢帧和等待；不能暗中给慢方法离线预计算。
- [ ] 方法输出接同一底盘执行/碰撞防护接口，在物理单位和限速上保持一致。不要强行改变UniGoal高层规划，也不要照搬Habitat归一化动作到实机速度。
- [ ] 正式方法运行时避免其他GPU重负载；不能一方独占、另一方与其他程序竞争而仍称同资源对照。

### 2.2 成功、预算与人工介入

- [ ] 为每个物理实例建立**仅评测使用**的instance ID和成功区域/参考位置。相同类别的不同椅子必须有不同ID。
- [ ] 预先固定成功规则，例如：自主停止、确为指定物理实例、机器人参考位置进入预先标注的允许区域；距离阈值若采用1m，明确从哪个点量到哪个点，且两方法相同。不要只用类别正确或高匹配分数判成功。
- [ ] 预算以**每目标墙钟上限**为主，可叠加共同的最大行驶距离；具体值依据demo/pilot耗时设定后，在正式采集前冻结。记录规划steps作为辅助，不能仅用两方法各1000个异构动作认定实机预算公平。
- [ ] 墙钟从“目标被交付并开始处理”到自主停止/预算终止，计入LLM、匹配、规划、等待新观测和运动时间。首次加载是否另计需一致并明确。
- [ ] 人工重定位、移动机器人、指定候选、手动指出目标均记录。正式自主SR不把人工救援计成功。因设备断连等基础设施错误的重试规则事先固定，保留首次日志和retry原因。
- [ ] 各方法启动顺序交替/随机化；记录环境变化、照明、人员/动态障碍，避免总是先跑Ours或总是先跑UniGoal。
- [ ] goal图先采集并冻结，测试前不让任一方法预建测试场景地图或提前缓存该任务的LLM规划结果。

### 2.3 UniGoal的LLM/VLM条件

- [ ] 保留UniGoal方法所需的LLM/VLM规划。**使用LLM本身不构成不公平，资源、输入和计时不透明才会破坏可比性**；不能为了看起来公平就删掉其核心规划。
- [ ] 固定模型名称、revision/digest、量化、提示词、服务地址和超时/重试设置。历史仿真配置为`llama3.2:3b`及`llama3.2-vision:latest`，这是历史实现，不自动等于实机最终配置；正式实验不能只记录浮动的`latest`。
- [ ] 如使用小模型、本地替代或不同于论文的服务，在表注中说明变体；不得笼统宣称完全复现原UniGoal官方配置。
- [ ] LLM/VLM总调用数、单次请求/返回时间、失败/重试、网络等待及总token（可得时）落盘。最终任务时间必须包含这些成本。

## 3. 第二步：日志和评测先落地

负责人：评测同学；这一项不要等导航跑完才补。

### 3.1 每次运行必须保存

| 层级 | 最少字段 |

| 系统 | ROS bag/等价传感器与位姿记录、控制命令/执行状态、CPU/GPU/RSS、LLM/VLM请求计时、进程退出码 |

### 3.2 必须提前跑通的统计

- [ ] 从一条短日志生成逐任务表，而不是手工抄终端数字。
- [ ] SR用外部评测标签；`localization_complete`单独一列。
- [ ] 路程由同一外部定位轨迹计算，两方法使用相同采样和滤波规则，原轨迹保留。
- [ ] **SPL只在有可靠最短可行路径时计算。** 评测用独立参考free-space地图/可达区域，不能让方法的预测地图为自己定义GT最短距离。没有可靠参考则先报告SR、距离和时间，不编造SPL。
- [ ] 多目标第k目标的SPL参考距离，从该方法在该次运行T_k的**实际起点**算到目标成功区域；不能把所有方法T2–T5的起点都当成序列初始位置。
- [ ] 运行耗时日志分routine perception/mapping、定位/确认、LLM、控制等待和运动；计时注明是否CUDA同步，异步模块注明是计算时长还是主线程阻塞时间，嵌套模块不重复相加。

## 5. 第四步：单目标pilot及正式定量对照

### 5.1 Pilot（仅调试，不混入正式结果）

- [ ] 固定3–5个开发任务，两方法各跑一遍；如果接口或参数有调整，保留每次尝试。
- [ ] 对照RGB-D/位姿对齐、控制单位、成功判定、LLM等待、峰值内存及错误退出。
- [ ] pilot结束后冻结算法与模型配置、任务清单、预算和统计脚本。

### 5.2 推荐正式规模（规划建议，不是已获结果）

- 建议**20个固定起点—目标任务 × 2方法 × 2次重复 = 80次单目标运行**。
- 场地允许时覆盖至少2个区域/布局，包含多个类别和同类干扰实例；任务不按任何方法成功结果筛选。
- 资源不足时先完成同一份清单上每任务各1次，再均衡增加重复，不能只给失败少或表现好的方法追加样本。
- 正式实验过程中若必须改算法，升版本并对受影响的共同任务重新成组评估，旧、新版本不混合择优。

主表：SR、SPL（条件满足时）、平均实际路径长度、平均任务墙钟、人工介入/碰撞事件。Steps与模型/定位runtime作为补充。所有失败包含在预算和终止口径中，成功子集指标另列分母。

## 6. 第五步：多目标功能验收——先2目标，再5目标

负责人：多目标调试同学；这是状态机验收，不是正式结果采集。

### 6.1 两目标切换必须覆盖的情况

- [ ] T1成功 → T2，机器人位姿不重置。
- [ ] T1超时/失败 → T2，仍可继续；除安全/设备异常必须终止外，前目标失败不结束整个序列。
- [ ] 不同类别切换；同类别不同物理实例切换。
- [ ] 新目标在历史地图出现过；新目标完全未出现过。
- [ ] 不提供未来目标图像给policy；评测端可知道完整顺序，但算法每次只收到当前query。
- [ ] 停止、切换、计时重置与目标结束事件无重复计数，终止原因明确。

### 6.2 两方法的记忆契约

| 方法 | 应保留 | 应按query清理/重建 |
|---|---|---|
| OSGSNav Shared | Gaussian/占据地图、实例历史、keyframe及相关持久地图状态 | 目标图与类别、当前候选/拒绝集、定位/PVA/query导航状态、目标条件评分 |
| UniGoal-M | BEV、collision/visited规划记忆、已有scene graph节点/对象/边 | 目标图、query匹配/临时目标、目标条件graph评分/子图、当前query恢复状态 |

- [ ] 在每次切换前后保存地图ID/大小/版本、pose、query ID、类别与goal hash，证明既没有误清图，也没有误重置机器人位置。
- [ ] 同类切换后不能沿用前一个物理实例的“已确认/已定位”状态。
- [ ] Ours现有服务器代码曾发现旧`_semantic_target`、mask/lock等目标状态残留风险；实机代码需实际核验当前query语义视图。不要直接把这个风险描述成已经修复或已造成某个结果。
- [ ] UniGoal-M验证`retarget_graph_preserving_memory`没有清空已观察scene graph，也没有让旧goal-conditioned评分继续支配新query。
- [ ] 若修复状态污染，单独提交、记录diff，冻结为新的实机多目标版本，不与修复前结果混统。

### 6.3 五目标pilot

- [ ] 用2–3条开发序列，每条5个不同物理实例，至少包含一次同类实例切换，两方法均执行。
- [ ] 检查4次切换、失败继续、预算逐目标重置、轨迹连续、未来图像不可见、日志能完整复算。
- [ ] 连续记录RSS/GPU内存/Gaussian/keyframe/graph规模。长时间记忆负担曾导致仿真实验资源保护停止，不能用单目标demo稳定代替五目标验收。
- [ ] 发生危及系统稳定的内存增长时停止并保留日志；不能通过给Ours偷偷清图来完成Shared实验。资源配额和保护阈值先冻结并记录。

**验收条件：** 两方法至少各有完整走完5个请求、4次正确切换的开发记录。允许导航失败，但协议必须完整、没有隐藏人工帮助。

## 7. 第六步：五目标正式定量对照

推荐规模：**10条预定义五目标序列 × 2方法 × 2次重复 = 40次序列运行、200个目标请求**。数量以机时为约束；先做每序列两方法各1次，再均衡补重复。若要扩大，优先增加独立序列/区域，而非只重复少数容易序列。这个规模是建议，不构成足够统计功效的保证。

- [ ] 每序列5个不同物理实例，至少一部分序列含同类别切换、跨区域返回和历史地图可复用目标。
- [ ] 所有序列在正式运行前固定，不能先跑Ours看成功再选目标顺序。
- [ ] 两方法使用相同T1初始位置/朝向、目标图和顺序，序列开始时均清空在线场景记忆。
- [ ] 序列内保留各自记忆和实际机器人位置，T1失败仍继续T2。**两方法从T2起实际位置不同是闭环结果的一部分**，不能人为把某方搬到对方位置；但要记录这些差异并正确计算每目标参考距离。
- [ ] 禁止把上一条序列的地图带入下一条正式序列，除非另外设计并单列了长期部署协议。
- [ ] OSGSNav-Clear不是本轮必需主对照。若后续需要实机记忆消融，可追加同清单的小规模Shared/Clear机制实验，资源不足时优先完成用户要求的Ours/UniGoal对比。

### 7.1 必需指标

| 指标 | 统计定义 |
|---|---|
| T1–T5 SR | 第k个目标的独立外部成功率，分母包含前面失败后继续执行的目标 |
| T1–T5 SPL | 仅在参考最短路径可靠时报告；使用各方法实际目标起点 |
| Per-target SR/SPL | 全部计划目标请求等权；因设备异常未执行的请求单独报缺失与原因，不默默缩小分母 |
| Prefix Ordered SR(k) | 同一次序列前k个目标全部成功的比例，非独立SR的乘积 |
| 距离/时间 | 每目标和整序列均值；包含失败、LLM等待和运动；成功子集另列 |
| 稳定性 | 完整序列比例、崩溃/人工介入/保护停止次数及原因 |

### 7.2 优先追加的记忆机制证据

- [ ] **定位前探索距离和墙钟**：从目标交付到首个显式内部定位事件，分别累计处于exploration模式的真实运动距离与时间；未定位请求保留到终止并单独标记。并列报告正确目标确认/最终成功，避免把内部定位当正确定位。
